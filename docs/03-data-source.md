# 03. 원본 데이터 소스 및 추출 규칙

## 1. 원본 자료

- **파일**: `docs/assets/korail-railroad-map-2026-01-01.jpg` (원본: `철도노선도(2026.1.1.).jpg`, 사용자 Desktop에서 저장소로 복사해 버전 관리)
- **발행처**: KORAIL 한국철도
- **기준일**: 2026.01.01, 단위: km
- **구성**:
  - 본지도: 전국 노선도 (지리적 배치, 노선/역/거리/본부 표기)
  - 좌상단 인셋(inset) 박스: 수도권 광역전철망 확대도 (본지도에서는 밀집되어 읽기 어려운 수도권 구간)
  - 좌하단 범례: 역 종류 8종, 선로 종류(단선/복선/비전철구간/광역전철운행구간/고속열차운행구간) 아이콘
  - 좌하단 "주요노선 구간·거리" 표: 22개 주요 노선의 기점~종점 및 총 거리(km), 기타 81개 노선 합계(659.7km), 전체 계 107개 노선 4,475.8km

이 문서는 이 이미지를 **구조화된 데이터(노선/역/구간)**로 옮기는 작업의 규칙과 절차를 정의한다.

## 2. 추출 대상 필드 (02-data-model.md 매핑)

| 지도 상 표기 | 데이터 모델 필드 |
|---|---|
| 노선명 (예: "경부선") | `Line.name` |
| 노선 색상/구간 구분 (범례의 단선·복선·비전철·광역전철·고속철도 선) | `LineStation.segment_track_type`, `segment_electrified`, `segment_speed_type` |
| 역 이름 및 점 표기 | `Station.name`, `Station.station_type` |
| 빨간 점(고속열차 정차역) | `Station.is_ktx_stop` |
| 역 사이 숫자(km) | `LineStation.cumulative_km` (구간 거리를 누적으로 환산) |
| 본부 라벨 박스 (예: "서울본부(서울)") | `Region.name`, `Region.hq_station_name` |
| 하단 "주요노선 구간·거리" 표 | 검증용 참고 데이터 (총 거리 크로스체크) |

## 3. 추출 방법

전체 107개 노선을 한 번에 정확히 옮기는 것은 비현실적이므로, 아래 원칙으로 단계적·검증 가능하게 진행한다.

### 3.1 수작업 판독 우선, OCR은 보조

- 지도는 손글씨 폰트가 아닌 인쇄체이지만, 선이 촘촘하고 숫자가 작아 OCR 정확도가 떨어질 수 있다.
- **1차: 사람이 육안으로 구간별로 확대해 읽고 표로 입력.** OCR은 후보 텍스트를 빠르게 얻는 보조 수단으로만 사용하고, 반드시 원본 이미지와 대조해 검증한다.
- 수도권처럼 노선이 밀집한 구간은 본지도 대신 **좌상단 인셋 확대도**를 기준으로 판독한다.

### 3.2 작업 단위: 본부(Region) 단위로 분할

이미지 자체가 본부별로 색상/영역이 구분되어 있으므로, 작업도 본부 단위로 나눠 진행한다. 예상 순서(제안, 지도상 밀도가 낮은 곳부터 시작해 방법론을 검증한 뒤 밀집 지역으로 확장):

1. 강원본부(동해) — 노선 수가 적고 지리적으로 분리되어 있어 방법론 검증에 적합
2. 충북본부(계천), 경북본부(영주), 대전충남본부(대전)
3. 전북본부(익산), 광주본부(광주), 전남본부(순천)
4. 대구본부(동대구), 부산경남본부(부산)
5. 수도권(서울본부/수도권서부본부/수도권동부본부) — 인셋 확대도 활용, 노선 밀도가 가장 높으므로 마지막에 진행

각 본부 작업이 끝날 때마다 해당 분량만 DB(또는 중간 JSON)에 반영하고 커밋 단위로 나눠, 전체 작업을 중단해도 부분 데이터가 항상 유효하도록 한다.

### 3.3 노선 단위 입력 규칙 (영동선 시범 추출로 검증·수정됨)

- 노선의 **기점**(0km 지점)을 먼저 정한다. 하단 "주요노선 구간·거리" 표에 기점~종점이 명시된 22개 노선은 그 표기를 그대로 기점으로 사용한다(예: "영동선: 영주~청량신호소" → 영주가 기점, 총 188.9km — 실제로 지도 위 끝 역 "청량"의 숫자와 정확히 일치함을 확인).
- 표에 없는 나머지 85개(기타 81개 지선 포함) 노선은 지도상 노선명이 시작되는 지점(대개 다른 노선과 분기하는 역)을 기점으로 정하고 `remarks`에 근거를 남긴다.
- **역마다 적힌 숫자는 이미 기점으로부터의 누적거리(`cumulative_km`)다.** (당초 "구간 거리를 누적으로 환산"이라고 적었던 것을 실제 지도 확인 후 정정 — 변환 작업이 필요 없고, 그대로 옮겨 적으면 된다.) 인접역 간 실제 구간 거리는 두 누적값의 차이로 계산.
- 범례에 `( ) = 참고 km`로 명시되어 있음을 확인. 즉 **괄호 안 숫자는 그 역이 놓인 "다른 노선"에서의 누적거리 참고값**이다(환승/분기 표기가 아님). 예: 영주역의 "188.3(115.0)"은 188.3이 중앙선상의 누적거리, 115.0은 경북선(김천~영주, 총 115.0km로 표 일치) 누적거리를 뜻함. 백산역의 "91.3(104.1)"은 91.3이 영동선 누적거리, 104.1은 태백선(제천~백산, 총 104.1km로 표 일치) 누적거리. 따라서 괄호 숫자를 만나면 **그 역이 속한 또 다른 노선의 이름과 해당 노선에서의 누적거리**로 해석해 `LineStation`에 별도 행으로 기록한다(같은 역이 두 노선에 속하는 것이므로 자연스러운 경우).

### 3.4 역 종류·선로 종류 판독 규칙

- 역 종류(`StationType`)는 범례 아이콘 모양·색으로 판별한다(9종, `02-data-model.md` 4.1 참고). 애매한 경우(예: 무인역과 신호장 구분이 어려운 작은 아이콘) `remarks`에 "판독 불확실"로 표시하고 넘어간다 — 나중에 일괄 재검토한다.
- **고속열차 정차역(빨간 원)이 표시된 역은 원래의 역 종류 아이콘이 가려져 보이지 않는다.** 이 경우 `station_type`은 정황상 추정치로 채우고 `remarks`에 "고속열차 정차역 표시로 원 아이콘 가려짐, 추정치"라고 남긴다.
- `is_ktx_stop`(고속열차 정차역, 빨간 점)은 다른 역 종류 아이콘과 겹쳐 그려질 수 있으므로, 확대해서 겹침 여부를 확인한다.
- 선로 종류(단선/복선)와 운행구간(비전철/광역전철/고속철도)은 **선의 색과 굵기**로 판별하며, 구간 중간에 종류가 바뀌는 지점은 그 지점을 기준으로 `LineStation` 행을 분리한다(즉 선로 종류가 바뀌는 지점도 하나의 "역/지점"으로 취급될 수 있음 — 실제 역이 아니면 무시 가능, Phase 2 착수 시 재확인).

## 4. 중간 산출물 포맷

DB에 바로 입력하기 전에, 검증 가능한 사람이 읽기 쉬운 중간 포맷으로 먼저 정리한다.

- 노선 하나당 CSV 또는 JSON 파일 1개, 경로: `data/raw/lines/<노선명>.json` (예: `data/raw/lines/경부선.json`)
- 스키마 예시:

```json
{
  "lineName": "경부선",
  "segmentLabel": null,
  "region": ["서울본부", "대전충남본부", "대구본부", "부산경남본부"],
  "stations": [
    { "name": "서울", "cumulativeKm": 0.0, "stationType": "MANAGED", "isKtxStop": true },
    { "name": "영등포", "cumulativeKm": 8.0, "stationType": "STAFFED", "isKtxStop": false }
  ],
  "sourceNotes": "판독 불확실 구간이나 특이사항 기록"
}
```

- 이 JSON 파일들이 Phase 2(데이터 구축)의 실질적 산출물이며, Phase 3(백엔드)에서 DB 시딩 스크립트가 이 파일들을 읽어 `Line`/`Station`/`LineStation`으로 변환한다.

## 5. 검증 방법

- **총 거리 검증**: 하단 "주요노선 구간·거리" 표에 기재된 22개 노선은 입력 완료 후 `총 거리(마지막 누적km)`가 표의 값과 일치하는지 대조한다.
- **전체 합계 검증**: 모든 노선 입력이 끝나면 107개 노선 총합이 4,475.8km(범례 하단 "계")에 근접하는지 확인한다(기타 81개 지선 659.7km 포함).
- **환승역 교차 검증**: 여러 노선에 동시에 등장하는 역(예: "서울", "대전", "동대구")의 이름 표기가 노선마다 완전히 동일한 문자열인지 확인한다(오타로 인해 같은 역이 다른 역으로 인식되지 않도록).

## 6. 다음 단계

데이터 추출 규칙이 확정되었으므로, 실제 데이터 구축(`data/raw/lines/*.json` 작성)에 착수하거나, 순서를 바꿔 `docs/04-api-design.md`(백엔드 API 설계)를 먼저 진행할 수 있다. 데이터 구축은 분량이 크고 반복적인 작업이므로, API/DB 스키마가 먼저 구체화된 뒤 착수하는 것을 제안한다.
